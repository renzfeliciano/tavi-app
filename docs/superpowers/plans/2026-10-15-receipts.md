# Receipts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A business can issue a numbered Collection Receipt or Acknowledgement Receipt for money that is not an invoice payment, download it as a PDF, email it, and void it with a reason.

**Architecture:** A new `receipts` table in the `payments` module (not an optional invoice on `payments`). `issueReceipt` takes the next `REC-` number from the existing receipt series inside one transaction with its audit event and optional outbox emails. The existing acknowledgement paper and PDF draw the receipt through a new view-model. Pages live under `/receipts`, reached from the Payments page and the New menu.

**Tech Stack:** Next 16.4 App Router, React 19, Drizzle/Postgres, Base UI/shadcn, Vitest, Playwright, `@react-pdf/renderer`.

**Spec:** `docs/superpowers/specs/2026-10-15-receipts-design.md`

## Global Constraints

- Tests first: write the test, watch it fail for the right reason, then implement. Run lint, typecheck, `npm test`, integration and e2e before delivery. Do not commit or push unless the user asks; commit messages carry no co-author or session trailers.
- Module boundaries are lint-enforced: import other modules only through `@/modules/<name>` or `/client`; only `application/`, `infra/`, `schema.ts` and tests touch the database; `domain/` is pure; only a file named `schema.ts` references another module's tables.
- Every signed-in page and action starts with `requireOrgContext()`, then `assertCan` / `can`. Permissions reuse `payments.read`, `payments.record`, `payments.void`; no new ones.
- Money is integer minor units plus a currency; dates are `YYYY-MM-DD` strings; "today" is `todayIn(timezone)`.
- Audit events are written inside the same transaction as the change; add new actions to `AUDIT_ACTIONS`.
- No hardcoded market values (D12): titles, notice and examples come from `src/config/markets.ts`; limits are named constants read by the rule, the form `maxLength` and the message (`tooLong(max)`).
- Carbon Copy design: violet only where ink would go, semantic tokens only, no entrance animations or gradients. Every page has its own `loading.tsx` skeleton in that page's real layout (`src/app/loading-states.test.tsx` enforces it). Every list is a `DataTable` with fixed-height scrolling panel, pagination, page size, count, debounced search.
- Every text field shows an example with `eg()` (`field-placeholders.test.ts` enforces it). Feedback standard: toast on every action; a dialog before anything hard to undo.
- A new folder under `src/app/(app)` goes in `PROTECTED_PREFIXES` (`src/shared/security/headers.ts`).
- New tenant tables go in the privacy export (D16) and `docs/compliance/processing-register.md`; made-up data only in tests; the landing page is not touched; do not run prettier on existing files.
- Integration and e2e run only against the test database and never at the same time.

## Review Focus

1. Two submits of the same receipt (double click, same idempotency key) make one receipt; two different receipts issued at the same moment get consecutive `REC-` numbers with no gap (Task 3).
2. A refused issue (bad input, a customer from another business or an archived one) must not use up a number: the next successful receipt follows the last one (Task 3).
3. A date received of today (in the business's time zone) is accepted and tomorrow is refused, including just after midnight in the business's zone (Tasks 1 and 3).
4. A payer name or purpose containing `<`, `&` or quotes is shown and emailed escaped, and a name of only spaces is refused (Tasks 1, 3 and 5).
5. Voiding twice, or viewing or voiding another business's receipt, gives a plain "not found" or "already void" and changes nothing; a voided receipt stays in the list and its page and PDF say it is voided (Tasks 3 and 7).
